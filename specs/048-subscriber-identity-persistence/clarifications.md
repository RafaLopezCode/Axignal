## Dependencies that must be resolved before subscriber runtime

1. Select an authentication approach only after verifying its support for Spec 022's Google-first and verified-email/password + provider-owned TOTP/recovery policy; record hosting/data-location and session/revocation evidence. No provider is selected here.
2. Define a trusted onboarding operation for first-time subscriber identity â†’ Principal â†’ Tenant and initial membership. Specify who may invoke it and its idempotency/abuse/recovery behavior. It must not be derived from email, payment metadata or Admin/Customer Zero authority.
3. Decide how a subscriber's 1/2/100 purchased capacity relates to payer, Principal, Tenant and Observation Focus. Leave all relationships `UNKNOWN` until the responsible product/billing authority decides them.
4. Select durable persistence architecture separately. Specify transaction and unique-key enforcement, lifecycle/deletion/retention, backup/recovery, consistency and migration/rollback. The offline contract does not settle these decisions.
5. Define production external error mapping and verify authorization/revocation under the real adapter, including two subscribers observing the same global Organization without private Focus leakage.

## Explicitly unresolved questions

- Issuer canonicalization and provider-specific assurance/session/revocation behavior.
- First Principal/Tenant/membership provisioning actor, ID allocation, abuse controls and transaction boundary.
- Principal/Tenant and payer/consumption cardinalities; roles/invitations; membership changes and final-member behavior.
- Tenant and Focus creation, pause, replacement, removal, retention and data-erasure policies.
- Durable storage engine, schema, migration, cache policy and production consistency window.
- Whether/when an external HTTP API exists and its endpoint-level rate/abuse controls.

No unresolved item is silently assigned a default. Offline fake tests may demonstrate only the contract outcomes they actually execute.
